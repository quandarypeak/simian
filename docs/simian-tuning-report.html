Tuning Simian Without Guessing

1 The trade-off, precisely

Every fuzzy-matching option in Simian trades precision for recall, or the reverse, and -threshold trades both against each other along a different axis. Loosen either lever and you will eventually catch a real duplicate that a stricter configuration missed, a true positive. Loosen either lever too far and you will start catching coincidences, structurally identical code that has nothing to do with duplication worth fixing, a false positive. There is no setting that maximizes both at once for every codebase; the right configuration is a property of the source you are scanning, not a property of Simian.

This report is about the workflow for finding that configuration deliberately, verified against a real, reproducible example rather than asserted in the abstract. It assumes the mechanics from the two companion reports: how -threshold sets a sliding-window size and how the TokenVisitor chain canonicalizes each line before it is hashed. What follows is about combining those mechanics on purpose.

2 Two knobs, not one dial

It helps to keep the two levers conceptually separate, because they fail in different ways.

  • Threshold answers "how many consecutive matching lines count as a duplicate worth reporting." It is completely blind to why two blocks matched. Raising it filters out short coincidences regardless of their cause; lowering it admits shorter coincidences regardless of their cause. It is a blunt, content-agnostic backstop.
  • TokenVisitor options (-ignoreVariableNames, -ignoreTypeAnnotations, -ignoreIdentifiers, and the rest of the catalog) answer "what counts as the same line." Each one erases a specific kind of cosmetic difference. They are precise about what they erase, but blind to where: an option that correctly reveals a duplicated algorithm will just as happily reveal a coincidentally identical getter, if both happen to canonicalize to the same text.

Section 6 plots six real runs of the same file on both axes at once. The short version: threshold alone cannot fix a false positive caused by an over-broad option, and no option choice can fix a false negative caused by too high a threshold. Both levers have to move.

3 Why the source dictates the start

The two companion reports already establish that different languages need different TokenVisitor wiring. The same is true, more broadly, of different kinds of source within one language, and it is worth naming the patterns before touching a single option:

  • Boilerplate-heavy OOP code (getters, setters, constructors, equals/hashCode) produces many short blocks that are structurally identical by convention, not by copy-paste. This is exactly the shape of false positive that aggressive identifier-erasure options manufacture, demonstrated concretely in section 6.
  • Generated or templated code (protobuf output, ORM-generated accessors, scaffolded test fixtures) is often deliberately repetitive. Simian will find the repetition accurately; the judgment call is whether that repetition is actionable. Excluding generated directories outright (section 4) is usually more honest than tuning options to hide them.
  • Test suites frequently repeat a setup/assert shape across many cases on purpose (that is what a table-driven test is). A threshold tuned for production code will over-report here; a separate, higher threshold or a narrower option set for test directories is often warranted.
  • Type-annotation-heavy TypeScript and generic-heavy Java hide real duplication behind cosmetic type differences, the exact case -ignoreTypeAnnotations and -ignoreSubtypeNames exist for (see the TypeScript chapter of the companion algorithm report).
  • Indentation-only languages (Python) do not need a different threshold in principle, since Simian counts significant lines rather than indentation levels, but short, deeply nested helper functions common in Python can still sit right at the threshold boundary and deserve a second look when they first appear in a report.

None of this changes the mechanism. It changes where you should expect to start on the two axes from section 2, and what kind of false positive to watch for first.

4 Step zero: exclude before you tune

The most common tuning mistake

No combination of -threshold and TokenVisitor options can fix "we found duplication inside a vendored copy of a library" or "we found duplication between generated files and the template that generated them." That is a file-selection problem, not a fuzzy-matching problem. Narrow the input with -includes/-excludes, or wrap known-noisy regions in -ignoreBlocks, before spending any effort on the options in this report. Tuning options against untrimmed input just makes the real signal harder to see underneath the noise.

Once the input set is a codebase's own hand-written source, the remaining tuning question is entirely about the two knobs from section 2.

5 The tuning workflow

The workflow below is deliberately a loop with small, single-variable steps rather than a search for the "right" settings in one attempt. Changing one lever at a time is what makes each new match, or each match that disappears, attributable to a specific decision; changing several things at once produces a result you cannot explain.

  1. Run with the defaults (or, for a first pass, whatever threshold roughly matches your team's idea of "a meaningful block," commonly 6 to 10 lines). Do not enable any fuzzy-matching options yet.
  2. Read the matches, not just the count. -reportDuplicateText is not optional at this stage: a count with no text tells you nothing about whether a match is real duplication or a coincidence.
  3. Classify what you see against three outcomes: nothing found (suspicious if you already know of duplicated code), matches that are all clearly real, or matches that include something you would not have flagged yourself.
  4. If real duplication is being missed, loosen exactly one lever: either the single narrowest option that would erase the specific cosmetic difference you can see in the source (section 7), or the threshold, by a small amount. Re-run.
  5. If a match looks like a coincidence, tighten exactly one lever: swap a broad option for a narrower one that still catches your real case (section 7), or raise the threshold, or exclude the specific file or block. Re-run.
  6. Repeat 2 through 5 until a pass produces no new surprises, neither obviously-missing duplication nor obviously-wrong matches.
  7. Validate before trusting the result (section 9), then record the configuration next to the codebase it was tuned for, since section 3 means it will not transfer unchanged to a different one.

6 Worked example: catching one, not two

The file below defines two genuinely duplicated methods (computeSubtotal and computeShippingCost run the identical accumulation loop over different parameter names) and two unrelated one-line getters that happen to share the same shape by convention, not by copying:

public class Ledger {
    private String name;
    private String description;

    public int computeSubtotal(int price, int qty) {
        int total = 0;
        for (int i = 0; i < qty; i++) {
            total += price;
        }
        return total;
    }

    public int computeShippingCost(int rate, int units) {
        int total = 0;
        for (int i = 0; i < units; i++) {
            total += rate;
        }
        return total;
    }

    public String getName() {
        return this.name;
    }

    public String getDescription() {
        return this.description;
    }
}

Six real runs against this file, moving one lever at a time, trace the full shape of the trade-off:

Run 1 and 2 are section 5's step 1: nothing found, and the source is known to contain a duplicate, so the verdict is "too few." Run 3 loosens both levers at once (low threshold, the broadest identifier option) and finds the real duplicate, but also the two getters, once -ignoreIdentifiers blanks every non-keyword identifier including the method names getName and getDescription themselves, both getters canonicalize to public String _ ( ) return this . _ ; and collide. Run 4 shows threshold alone can rescue precision here, raising it from 2 to 3 drops the 2-line getter match while keeping the 5-line real one. Run 5 shows the more robust fix: -ignoreVariableNames only blanks identifiers classified VARIABLE, and a method name followed by ( is classified METHOD (see the companion TokenVisitor report, section 5), so getName and getDescription are never touched and the getters simply do not match at any threshold. Run 6 closes the loop: push threshold to 5 with the correct option and the real duplicate, only 4 significant lines long, disappears again.

7 Prefer narrow to blunt

Run 4 and run 5 in the worked example reach the same correct answer by different means, and the difference matters beyond this one file. -ignoreIdentifiers is the broadest identifier-side option: it erases every non-keyword identifier, method names included. -ignoreVariableNames is narrower: it only erases identifiers already classified VARIABLE by RecogniseIdentifiersTokenVisitor, leaving method names, type names, and constants untouched. The broad option worked in run 4 only because the threshold happened to be raised enough to compensate; the narrow option in run 5 was safe by construction, because it never had the power to make two differently-named methods collide in the first place.

As a general rule: reach for the option that erases exactly the cosmetic difference you can point to in the source (a renamed variable, a changed type annotation, a different string literal), and reach for the broad, all-erasing options (-ignoreIdentifiers, -ignoreLiterals) only when the narrower ones genuinely do not cover the case. The broad options are not wrong to use, they are simply harder to reason about, since they collapse more distinctions than most single duplicate has actually changed, which is exactly what widens the door to coincidental matches like the getters above.

9 Validating without ground truth

Most real codebases do not come with a labeled list of "these blocks are duplicates, these are not," so validating a configuration means manufacturing a small amount of ground truth on purpose:

  • Seed a known duplicate. Copy a real block you know should be flagged (or use one already fixed by a past refactor, reverted locally) and confirm the candidate configuration still reports it. This is a regression test for the configuration itself, and it is worth keeping alongside the configuration for the next time thresholds change.
  • Spot-check a sample of real matches. Read the actual text of five or ten reported blocks with -reportDuplicateText, not just the summary counts. A configuration that "finds 400 duplicate blocks" says nothing about quality until a human has read a sample of them.
  • Watch the count when you change one thing. A large jump in matches after enabling a single option is itself a signal, worth treating as "too many" in the workflow of section 5 until proven otherwise by reading the new matches.
  • Re-validate after the codebase changes shape. A configuration tuned against today's mix of hand-written and generated code can start reporting differently once a new generated module, or a new boilerplate-heavy layer, is added. Section 3's advice is a function of the source, and the source moves.

11 Conclusion

Tuning Simian well is not a single choice of numbers but a short, repeatable loop: run, read the actual matched text, change exactly one lever in the direction the evidence points, and re-run. Threshold and the TokenVisitor options are answering two different questions, how long a match must be and what counts as the same, and both have to be right together, as the worked example's safe corridor shows directly. The one habit that generalizes past any single codebase is the discipline of section 7: reach for the narrowest option that explains the difference you can actually see in the source, and only widen it when the narrow one demonstrably fails, because the broad options do not just catch more duplicates, they also stop distinguishing between duplication and convention.
